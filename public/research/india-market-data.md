# India travel data and fare collector

## Indian passenger traffic

Source: [Vonter/india-aviation-traffic](https://github.com/Vonter/india-aviation-traffic), [city-pair CSV](https://raw.githubusercontent.com/Vonter/india-aviation-traffic/main/aggregated/domestic/city.csv), derived from India's [Directorate General of Civil Aviation](https://www.dgca.gov.in/digigov-portal/) and [Ministry of Civil Aviation](https://www.civilaviation.gov.in/). The database is licensed under [Open Database License 1.0](https://opendatacommons.org/licenses/odbl/1-0/). Attribution, share-alike and keep-open conditions apply to public use of adapted databases. This dashboard's adapted per-route output is available through `/api/india-market/traffic?origin=DEL&destination=PNQ`; the application source describes the transformation. The unmodified database is also available at the source link.

The server fetches the source CSV on request with up to a 12-hour server cache. It validates expected headers and filters six configured directional routes; it does not collect bookings, searches, airline-specific route counts or TBO data. `PaxToCity2` counts City1 → City2 and `PaxFromCity2` counts the reverse. Any month with more than one matching record, including reversed records, is flagged ambiguous and excluded rather than automatically summed or deduplicated. Missing months are not zero-filled. The page displays the last 12 **recorded** months, which may have gaps. This conservative rule can discard valid observations where records refer to distinct airports or services; verify source workbooks before resolving ambiguities.

The displayed next-report-month reference is simply the same month one year earlier. A rolling historical test compares this rule against the observed 2025 monthly route totals where both values are available; MAE is in passengers. The test uses today's potentially revised dataset, not historical publication snapshots. Passenger data are published with a lag, and the next-report month may have already passed; this is not necessarily a future prediction. It does not model future fares, cancellations, TBO market share or operational inventory.

## Daily fare observation collector

An authenticated Vercel cron (`GET /api/cron/collect-fares`) is scheduled for 04:10 UTC daily; Hobby cron may run at any time within that hour and only runs in production. It checks six configured directional routes, at 1, 7 and 30 calendar days from the UTC collection day. For each combination it records the cheapest returned Travelpayouts v3 cached result in INR, or explicit empty/error state, in PostgreSQL `public.market_fare_observations`. `CRON_SECRET` protects the job, and the provider token stays server-side. Same-day repeats upsert by collection day, route and departure date, and an error/empty repeat cannot replace an existing successful observation. Database row-level security is enabled; no browser-facing Supabase policies grant access. The public dashboard API returns only the configured route observations, with no customer data.

The provider data is a cache of search results, not live or guaranteed fares, booking counts, searches on TBO or seats sold. Sparse coverage, changing provider inventories, different flights and sample selection make observations incomparable unless departure date, route, direction, currency and other available details are considered. Failure and empty responses do not mean sold-out or zero price. Check `provider_found_at` and expiration; old observations are historical, not offers. The collector starts on deployment/first run and cannot reconstruct past observations. Price forecasts are intentionally not generated before sufficient, validated history exists. No booking or procurement is automated.

Travelpayouts recommends caching its Data API for 24 hours; their documentation does not clearly establish long-term historical-retention rights for this use. Before relying on or using collected history commercially, confirm permissions and retention period with Travelpayouts under your partner agreement. This prototype does not auto-delete observations yet; you can delete the observations if required. Vercel Hobby is for personal non-commercial use; production commercial use requires a suitable plan and provider licences.

## Setup and operations

- Existing production `TRAVELPAYOUTS_TOKEN` and PostgreSQL `DATABASE_URL` are required.
- Add a random `CRON_SECRET` as a sensitive production environment variable before deploying. The job checks its bearer value; do not put secrets in Git.
- Run the migration in `docs/india-market-migration.sql` against the same database referenced by `DATABASE_URL` before the job runs. Supabase row-level security is enabled; direct server PostgreSQL access must use an authorized role.
- Vercel reads the cron schedule from `vercel.json`. The first scheduled run can take a day; an authorized operator can invoke the cron route once to seed it. Monitor collector and database errors; the page displays empty/error states rather than invented prices.
- India traffic comes from the public GitHub source at request time; no paid API is required. Vercel Hobby and Supabase free tiers have usage and eligibility limits. This is not a guarantee of zero cost in production.

A disabled-by-default seven-day matching pilot optionally adds a +23-day check when `FARE_HISTORY_PILOT_ENABLED=true`. Confirm provider retention rights before enabling it. See [seven-day fare methodology](/research/seven-day-fares.md). The existing collector still retains its original observations; the pilot setting does not change or delete them.

The separate **Can we forecast this route?** section applies a chronological retrospective test with a conservative freshness and benchmark gate. See [Indian traffic validation](india-traffic-validation.md) for the complete method. It does not use TBO transactions and does not drive procurement allocation.
